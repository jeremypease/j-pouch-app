# J-Pouch — project context

This is the working folder for the J-Pouch iOS app. See `jpouch-app-prd.md` in this same folder for the full product requirements document (problem statement, goals, user stories, P0/P1/P2 requirements, success metrics, timeline).

## Naming (finalized)

- **Home screen / in-app name:** `J-Pouch`
- **App Store Connect listing title:** `J-Pouch: Your Companion`
- Use "J-Pouch" everywhere in code, UI strings, bundle display name, and asset names. Reserve the longer "J-Pouch: Your Companion" for the App Store Connect title field only.

## Key product decisions

- Native SwiftUI, iOS only for v1 (no Android, no Apple Watch app — deferred to P2).
- Solo/light-dev build, ~3 month target for v1 (P0 scope only — see PRD Timeline Considerations).
- Freemium via subscription, not ads. Free tier = all core logging (output, hydration, food, meds). Paid tier gates caregiver view and future AI trigger-food suggestions.
- HealthKit integration (dietary water, body mass) is in P0 scope.
- No diagnosis language anywhere — dehydration/pouchitis pattern flags are framed as "bring this to your GI," never a medical determination.
- j-pouch.org has no public API; any tie-in is a content/linking partnership, not a data integration (open question, not yet resolved).

## Working style

Jeremy prefers concise, direct communication with minimal unnecessary explanation.

## Dev setup

- **Release from Xcode's GUI: Product → Archive → Distribute App → App Store Connect.** This is the default release path as of 2026-08-04. Cloud signing (`CODE_SIGN_STYLE: Automatic`, signed through the account under Xcode → Settings → Accounts) previously failed here with a "Cloud signing permission error" — that's now resolved and confirmed working end to end (archive, cloud sign, and processed successfully on App Store Connect). The cause was never fully root-caused; it may have been tied to the GUI-launch failure below, or an Apple-side fix. Run `xcodegen generate` first if `project.yml` changed since the last generate — the GUI won't do this for you.
- **Command-line fallback: `./Scripts/release.sh`.** Signs using an App Store Connect API key instead of an account added in Xcode's Accounts settings — see the header comment for the one-time key setup. Keep this around in case the GUI path breaks again, or for scripted/unattended releases.
- **Manual signing assets exist as a fallback, not the default.** `Scripts/create-signing-assets.sh` creates the distribution certificate and the "JPouch App Store" profile explicitly and installs both, for `release.sh` to use via the API key above — only needed if cloud signing breaks again. Run it once a year when the certificate expires, or if the profile needs reissuing. The signing private key lives in `~/private_keys/jpouch-signing/` outside the repo — **back it up**, since losing it means revoking and reissuing the certificate.
- **Team ID is `S6M9LCA6DC`.** Take it from developer.apple.com → Membership, never from a certificate name: the keychain also holds development certs whose parenthetical is a *user* ID, and using one of those produced a "No Account for Team" failure that looked like an entitlements problem for a while.
- **Archiving for TestFlight/App Store requires a released Xcode, not a beta.** App Store Connect rejects any build made against a beta SDK ("Unsupported SDK or Xcode version"), regardless of the app's deployment target. It must also be Xcode 26 or newer: the HealthKit Medications integration (`HKUserAnnotatedMedication` in `HealthKitManager`) only exists in the iOS 26 SDK and won't compile against anything older. Point at it with `sudo xcode-select -s /Applications/Xcode.app`; scripts here prefer `/Applications/Xcode.app` and fall back to `Xcode-beta.app`. Check with `xcode-select -p` before archiving — a build made against `Xcode-beta.app` will get rejected at upload even if it archives locally without error.

- Xcode project is generated by xcodegen from `project.yml` — never hand-edit `JPouch.xcodeproj` (it's gitignored and gets overwritten by `xcodegen generate`).
- **The `JPouchWidget` target needs the App Group capability enabled on the App ID in the Apple Developer portal (team `S6M9LCA6DC`) before it will build/sign.** `project.yml`/`xcodegen generate` declares `group.com.jeremypease.jpouch` in both targets' entitlements, but can't enable the App Group capability on the App ID itself — that's a one-time manual step at developer.apple.com. Until it's done, expect a provisioning failure on the widget target (not an obviously-labeled "App Group missing" error).
- One-time after cloning: `git config core.hooksPath .githooks` — activates the pre-push hook. It runs **the test suite first, which does block on failure**, then the `senior-apple-reviewer` subagent (`.claude/agents/senior-apple-reviewer.md`) whose findings are printed but **advisory only: the review never blocks the push.** It was originally a gate, but the model emitted the machine-readable verdict the gate depended on in only about a third of real runs, and the only BLOCK it ever produced was a false positive — so the review stays and the unreliable gate is gone. Read the findings, then decide. Requires the `claude` CLI on PATH; degrades to a no-op warning if it's missing. Skip the review with `git push --no-verify`.
